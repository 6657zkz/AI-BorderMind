# 目标架构

> 本文描述目标系统的工程架构、领域契约和演进约束，不描述当前已经实现的能力。当前可验证范围以 [current-state.md](current-state.md) 与代码/测试为准；唯一研发顺序与阶段门槛见 [roadmap.md](roadmap.md)；已实现模块的稳定边界见 [contracts/](contracts/README.md)；不可逆决定见 [adr/](adr/README.md)。

## 1. 架构目标与边界

AI-BorderMind 要建立的不是通用聊天机器人，而是一个从数据变化、业务事件到经营决策的受控系统。工程架构必须同时保证：

1. **数据优先**：结论基于可查询、可解释的数据证据，而非模型常识。
2. **受控动态性**：LLM 只能理解已注册的业务目标、范围和证据关系；不能执行任意代码、工具或 SQL。
3. **持续决策**：用户问题和监控信号都是入口，长期事项沉淀为可恢复的运行记录。
4. **可追溯性**：每个节点、查询、计算、结论和数据版本都能回放。
5. **横向扩展**：新增领域通过目录注册决策类型、任务、角色、数据能力、事件模式和策略，而不是复制工作流。

首期与后续演进均不允许：自由 LLM SQL、专家角色自由创建子 Agent、信号无条件升级研判、未经审批的改价/下单/预算变更，或为技术细节滥建任务节点。

## 2. 从事实到决策的领域链

目标业务主链如下：

```text
网络 / 平台 / 内部数据采集
  -> 原始事实数据
  -> 原子信号
  -> 复合事件
  -> 触发策略
  -> 决策类型
  -> DecisionGraph
  -> ExecutionPlan
  -> AnalysisRun / NodeRun
  -> 受控数据能力 + 专家判断
  -> EvidenceChain / EvidenceEntry
  -> 决策结果 / DecisionCard
```

| 层级 | 解决的问题 | 工程责任 |
|---|---|---|
| 数据采集 | 数据从何而来 | ingestion adapter 取得并落库，不作经营结论 |
| 原始事实 | 实际观测到什么 | 价格时序、评论、销量、库存、运费、汇率等带来源与版本的事实记录 |
| 原子信号 | 哪项指标在何范围和窗口越过阈值 | 检测器创建可独立展示、审计、失效的信号 |
| 复合事件 | 多个关联信号说明何种待验证现象 | 通用归并引擎按事件模式、范围、窗口、幂等合并信号 |
| 触发策略 | 此时应通知、建议还是自动研判 | 受限规则映射来源、条件、严重度和冷却期到动作 |
| 决策类型 | 业务最终要作什么行动 | 注册最小前提、任务蓝图、输出契约与失败规则 |
| 分析任务 | 为决策必须完成哪些可验证工作 | 明确输入、依赖、允许 Operator、质量和失败策略 |
| 专家角色 | 谁按哪种专业标准进行权衡 | Playbook 和结构化输出，不拥有数据库或编排权 |
| 数据能力 | 如何取得证据和确定性计算 | 受控 Operator、查询编译器或外部数据适配器 |

采集只负责取得和落库；分析、决策和专家角色必须通过受控的数据能力读取事实。替换爬虫、平台 API、ERP 或本地 fixture 不能改变决策、计划或证据语义。

## 3. 信号、事件、策略与决策类型

### 3.1 原子信号

原子信号是明确对象、范围、基线、当前值、时间窗、阈值、检测器版本和证据的可验证变化。例如“美国站 TWS 耳机竞品 P-102 在 24 小时内由 49.99 USD 降至 34.99 USD，下降 30%，命中 `price_drop_v1` 的 20% 阈值”。

信号必须可独立展示、独立审计、独立失效；同一个事实变化不能仅以聊天文案存在。

### 3.2 复合事件

复合事件是待验证业务假设，不是事实结论。例如同一项目、市场和竞品商品在重叠窗口内同时出现降价、销量上升和库存下降，可以形成“疑似强促销、清库存或平台补贴”。

归并引擎固定负责：范围匹配、实体关联、时间窗重叠、状态、去重和幂等。配置化事件模式负责：可组合的信号、阈值、持续时间、优先级和适用范围。未命中模式的信号仍作为独立信号存在。

### 3.3 触发策略

以下概念不得混用：

```text
复合事件：发生了什么业务现象？
触发策略：满足何种条件时系统采取什么动作？
决策类型：业务人员最终要决定什么经营行动？
```

触发策略是受限配置，字段包括来源、事件/候选决策类型、范围、严重度、置信度、阈值、优先级、动作、冷却窗口和幂等键。动作仅限：仅回答、仅通知/观察、建议研判、创建待审批 Run 或自动创建研判 Run。它不执行任务，也不替代决策类型蓝图。

高置信度事件可预填市场、竞品、商品和证据上下文；高影响动作仍只能生成证据化建议和人工复核条件。

### 3.4 决策类型与澄清

不同决策类型具有不同的最小决策前提，澄清必须由“决策类型 -> 任务契约”驱动，不能把“品类 + 市场”固化为所有对话的前置条件。

| 决策类型 | 最小决策前提 | 主要任务 | 典型输出 |
|---|---|---|---|
| 选品发现 | 市场、价格层级/预算、时间窗；品类可未知 | 机会扫描、需求趋势、竞争密度、价格带、评论缺口、供应可得性 | 候选品类排序和验证方向 |
| 品类进入评估 | 品类、市场；目标毛利可选 | 需求、竞争、价格带、成本/毛利、评论、综合评分 | 进入、观望或补充数据后复核 |
| 定价与价格卡位 | 品类、市场、SKU/成本边界、目标毛利 | 竞品价格、价格带、成本地板、毛利敏感性、方案比较 | 标价、优惠券、捆绑、跟价与复核阈值 |
| 竞品促销应对 | 竞品、市场、我方商品/价格、响应边界 | 促销核验、价格带影响、毛利/库存、替代方案 | 维持、发券、跟价、调整广告或观察 |
| 产品改良与卖点 | 产品/品类、市场、评论或售后范围 | 方面词、负面根因、竞品对标、需求缺口、可实现性 | 改良优先级、卖点、验证实验 |
| 搜索与流量机会 | 市场；品类可选 | 搜索趋势、供给覆盖、转化与内容缺口 | 关键词、内容主题、广告测试清单 |
| 补货与库存风险 | SKU/品类、市场、库存、在途、提前期 | 预测、覆盖天数、在途风险、安全库存 | 补货量、时间、调拨或限量建议 |
| 广告预算调整 | 广告活动/商品、市场、预算目标 | 流量、排名、漏斗、效率、价格/库存联动 | 加减预算、停词、拓词、竞价策略 |
| 供应链与到岸成本 | SKU/品类、采购/物流路径、成本边界 | 到岸成本、报价、交期、质量、利润影响 | 供应商、运输、调价与备货建议 |
| 市场准入与合规 | 市场、品类、销售模式 | 规则匹配、属性核验、缺口、成本与时效 | 暂缓、补认证、调整包装/Listing、换市场 |

目录可以登记目标决策类型，但只有任务、数据能力、证据和结论契约完整实现的类型才能被识别器选中并执行。

## 4. DecisionGraph 与 ExecutionPlan

### 4.1 DecisionGraph：业务理解图

DecisionGraph 表达一次用户请求或事件的业务语义：为什么要分析、要作什么决策、发生了什么、范围是什么、哪些约束存在、需要哪些证据和比较关系。它不是任务列表或直接运行的工作流。

```text
事件 -> 决策
决策 -> 所需证据
证据 -> 指标
指标 -> 实体
约束 -> 决策
竞品商品 <-> 我方商品的比较
```

例如竞品疑似促销可以关联事件、决策类型、美国站/TWS/竞品 P-102 的范围、30% 目标毛利约束，以及价格真实性、市场价格带、毛利和库存承受能力等所需证据。

识别器或 LLM 只能生成目录白名单中的候选实体、指标、约束和决策类型；未知引用必须在编译前失败。DecisionGraph 需要快照本次识别、触发策略、上下文、目录版本和约束，使历史 Run 不受未来规则文案变化影响。

### 4.2 ExecutionPlan：唯一可执行任务图

ExecutionPlan 由编译器根据 DecisionGraph、项目画像和能力目录生成，是程序唯一允许执行的 DAG。每个节点必须声明：

```text
任务标识与目的
依赖节点
允许的数据能力 / 专家角色
输入及其来源
质量条件
失败、跳过、澄清和重试策略
结构化输出与证据引用
```

例如“市场价格带影响评估”可以要求市场、品类和时间窗，调用价格分位数和价格带 Operator，限制样本量和数据时效，并输出 p25/p50/p75、趋势和 Evidence ID。下游“竞品促销应对建议”只能消费促销核验、价格带评估、毛利与库存承受能力等显式依赖的已验证 Evidence Package。

无依赖任务可并行；下游只能在显式依赖成功或按契约允许部分成功后运行。技术细节如 JSON 拼接或空值删除不应单独成为图节点，除非具备独立执行、复用、并行、重试或审计价值。

## 5. 任务契约、专家角色与数据能力

### 5.1 任务契约

每个分析任务应机器可读地定义：目的、必需输入、可选输入、允许 Operator、数据质量、硬规则、输出字段以及缺失/过期/失败处理。

定价建议任务的典型硬规则包括：常规售价不得低于成本地板；未经计算证据不得声称满足目标毛利；证据不足时不得伪造精确建议。缺目标毛利应结构化澄清，缺成本应阻塞相应任务，数据过期应刷新或明确标记不可用。

当某一工作需要访问外部数据、执行公式、可被多个节点复用、可并行/局部重试、需要不同专业标准或产物值得单独复核时，应拆为独立任务或数据能力。完整证据上的情景比较和专业权衡可保留为一个专家节点。

### 5.2 专家角色

专家角色是职责边界、输入检查、专业分析顺序、证据标准、不确定性表达、输出格式、升级规则和复核节奏的 Playbook。它不是自由 Agent，也不是独立工作流。

专家输入只包括任务契约、用户/事件上下文、项目画像与约束、上游已验证输出、数据质量和输出契约。专家可比较维持价格、降价、优惠券和捆绑等方案，并输出建议、替代方案、风险和复核阈值；程序负责验证成本地板、毛利和证据引用等硬规则。

### 5.3 数据能力与 Operator

固定 Operator 是首期取证的安全边界，可实现市场价格分位数、成本查询、毛利敏感性、评论方面词、库存覆盖、异常检测和趋势计算。每个 Operator 必须负责参数校验、受限只读访问、结果限制、质量元数据和 Evidence 格式。

Operator 不决定应否执行任务；该决定来自经过编译的 ExecutionPlan。专家、API、前端和 LLM 都不能直接使用 Operator 绕过计划。

## 6. 能力目录与模块边界

能力目录是系统的唯一注册表和安全边界，统一登记：实体与指标、数据能力、任务契约、专家 Playbook、决策类型蓝图、复合事件模式和触发策略。不得让 persona、planner、前端或静态工作流维护第二套依赖关系。

新增“补货决策”等能力的正确路径为：注册决策类型 -> 注册任务契约 -> 注册需求预测/库存覆盖等数据能力 -> 注册库存专家 Playbook -> 注册相关信号和事件模式 -> 注册触发策略。仅新增一个 Prompt 文件不构成新能力。

工程保持模块化单体，依赖方向为：

```text
HTTP / SSE / Vue DTO
  -> Application Service
  -> Domain
  -> Ports / Protocols
  -> Infrastructure Adapter
```

| 模块 | 负责 | 不负责 |
|---|---|---|
| 能力目录 | 类型、任务、角色、数据需求和策略的登记 | 执行 SQL 或 LLM |
| 决策规划 | DecisionGraph 校验与计划编译 | HTTP、ORM 会话或直接查询 |
| 分析运行 | Run/NodeRun 状态机、DAG 调度、重试、超时、取消 | persona 常量或路由逻辑 |
| 查询能力 | Operator、检测器、未来受控指标查询 | 决定业务上是否执行能力 |
| 监控与策略 | 信号、事件、触发、去重、冷却 | 直接调用 Chat 路由 |
| 证据 | 证据规则、存储、读取、脱敏、截断 | 以内存缓存作为权威来源 |
| 项目与会话 | 项目画像、会话、消息、范围抽取 | 编排研判任务 |

API 仅做 DTO、认证/注入、服务调用和协议映射；不得直接操作 ORM、LLM、LangGraph、Operator、线程或完整 Run 状态机。物理目录必须服务职责边界，不能为了“分层”创建空抽象、循环依赖或兼容性平行工作流。

以下目录是目标模块化单体的物理组织约束，用于承载第 1 至第 7 阶段的能力；它不是当前工作区已实现文件清单。目录只能在所属阶段需要真实职责时创建，禁止为凑结构预建空模块或用兼容层保留被退役的流程。

目录职责必须满足以下规则：

| 目录 | 允许依赖和职责 | 禁止事项 |
|---|---|---|
| `api/` | DTO 校验、身份/依赖注入、协议映射、调用 service | 直接操作 ORM、Operator、LLM、线程或 DAG 状态机 |
| `service/` | 用例协调、事务边界、领域对象与端口编排 | 把业务规则复制进 HTTP DTO 或基础设施适配器 |
| `domain/` | 领域契约、状态机、编译器、端口与业务校验 | 依赖 FastAPI、SQLAlchemy、网络 Client 或 Vue |
| `infrastructure/` | 实现 domain 声明的端口，封装数据库、LLM、调度和工作流引擎 | 决定决策类型、任务依赖或绕过 ExecutionPlan 执行 Operator |
| `web/src/features/` | 按用户工作流组织页面和状态 | 按固定决策类型、节点数量或结论字段硬编码流程 |
| `web/src/api/` | HTTP/SSE 协议 Client 与 DTO 转换 | 保存业务编排、执行状态真源或直接推导结论 |
| `db/` | 可审阅的 schema、迁移和受控 seed | 作为应用层业务逻辑或 fixture 真源 |

建议按阶段落位：第 1 阶段仅需要 `capabilities/`、`planning/`、`analysis_runs/` 的规划契约和相应 API/service；第 2 阶段增加 `projects/`、`sessions/` 与受控识别；第 3 阶段引入 `infrastructure/db/` 和根目录 `db/`；第 4 阶段增加 `workflow/`、`scheduling/` 的适配器；第 5 阶段增加 `monitoring/`；第 6 阶段按 feature 创建前端工作区；第 7 阶段才创建 `planning/text2sql/`。`infrastructure/llm/`、部署文件和 `chat_compat.py` 仅在真实需求和对应 ADR 通过后创建。

## 8. 运行、恢复与证据持久化

每个用户请求、人工确认或事件触发均应形成独立 AnalysisRun，保存触发来源、用户问题、项目画像与信号上下文快照、DecisionGraph、ExecutionPlan、节点输入输出、错误/重试/耗时、最终结论、证据链和数据版本。

目标 Run 状态机：

```text
created -> planning -> waiting_clarification -> planned -> running
  -> succeeded / partial_succeeded / failed / cancelled / timed_out
```

目标节点状态机：

```text
pending -> ready -> running -> succeeded / skipped / failed / timed_out
```

`skipped` 必须记录数据不足、条件不满足或能力未启用等原因。失败按任务契约有限重试，只重试失败节点。用户补充字段后，复用同一 Run 的已成功节点与证据，仅恢复阻塞节点及其下游。

SSE 只是订阅层；断开连接不能取消后台 Run。数据库是 Run、NodeRun、Evidence 和结论的权威来源，内存结构只可作为缓存或 DTO。前端依据 Run 与 NodeRun 状态展示进度，而不是从聊天文本猜测。

## 9. API、SSE 与前端演进

目标 API 以运行记录为中心：

```text
POST /api/chat/sessions
GET  /api/chat/sessions/{session_id}
POST /api/chat/sessions/{session_id}/messages

POST /api/analysis-runs
GET  /api/analysis-runs/{run_id}
POST /api/analysis-runs/{run_id}/clarifications
POST /api/analysis-runs/{run_id}/cancel
GET  /api/analysis-runs/{run_id}/events
GET  /api/analysis-runs/{run_id}/evidence
POST /api/signals/{signal_id}/analyze
```

Chat 只处理会话校验、范围抽取、消息写入、创建/订阅 Run。非流式和 SSE 入口必须共享同一个应用服务与运行链，不能各自维护业务规则。

目标工作台以 Chat 为主入口，显示会话、候选决策类型、已提取上下文、缺失字段、澄清卡、DecisionGraph、ExecutionPlan、节点状态、结论和证据。标题、节点和结论不得硬编码为任意决策类型。信号页应能追踪“信号 -> 复合事件 -> 研判 -> 结论”。

## 10. 真实数据、LLM 与受控取证规划

接入真实数据前必须补齐数据源适配器、项目/租户隔离、权限、参数限制、查询成本、结果截断、版本、质量校验和完整审计。模型推断必须与原始事实和确定性计算明确区分。

LLM 合法职责仅包括：白名单内决策候选识别、结构化上下文提取、澄清草案、计划/证据解释，以及基于已验证 Evidence Package 的结构化专家判断。它不得发明目录项、访问完整 schema、持有数据库连接、生成并执行原始 SQL、调用任意网络/文件/工具或执行经营动作。

在固定 Operator 无法覆盖的后期任务中，可引入独立的受控取证规划节点：

```text
任务契约 + 能力目录 + Ontology + 上下文
  -> LLM 输出 MetricQueryGraph
  -> 确定性授权与白名单校验
  -> 映射为 Operator 或参数化只读 SQL
  -> 查询、质量校验和证据持久化
  -> 专家节点消费 Evidence Package
```

`MetricQueryGraph` 只能表达实体、指标、维度、过滤、时间窗、聚合、比较、范围、输出字段、质量要求和证据用途。Ontology 必须受控登记业务实体、指标定义、维度、关系、合法 Join、时间语义、允许聚合/过滤/比较、权限和默认限制。

编译器必须强制白名单表/列/Join、不可移除的租户条件、只读参数化执行、超时/扫描/行数预算、质量校验与审计。任何校验失败必须在执行前失败；自由 LLM SQL 永远关闭。

## 11. 架构决定

涉及持久化权威来源、公开 API、能力目录所有权、执行语义、租户/权限模型或 LLM/数据访问边界的不可逆变更，必须新增 `docs/adr/` 中的 ADR。普通实现细节不需要 ADR。
